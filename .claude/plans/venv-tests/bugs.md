# venv-tests - bugs

## needs a decision - in scope (this plan created the affected service)

- **`mongo:8` container segfaults, both under load and idle**: reproduced three times. `docker-compose.dev.yml`'s new `mongo` service (added phase 0) crashes with exit code 139 (SIGSEGV). crash 1 and 2: partway through `tests/python/component/` (coverage-wrapped, full suite) during heavy collection-drop/index-teardown activity, ~40+ minutes apart. after each, every remaining component test in that run fails with `pymongo.errors.ServerSelectionTimeoutError` instead of its real result - the "component tests FAILED, 1628s, no pass/fail count" line in `run_tests.py`'s results table is this crash, not a slow/hanging suite. **crash 3 (2026-08-29, found during shipdown): load-free.** restarted the container between phase 1 and phase 2 (no test load applied during phase 2 - pure docs/config edits); `docker inspect` shows `StartedAt: 02:04:00.86`, `FinishedAt: 02:04:30.50` - it crashed 28 seconds after a clean startup while idle. `docker logs` confirms: normal startup completing ("mongod startup complete", "Waiting for connections" at 02:04:01.965) followed by zero further log output before the process died - no warning, no error, nothing. **revised conclusion: this is not purely a sustained-load issue - the container is not reliably stable at all**, idle or under load.
  - ruled out: not OOM (`docker inspect`: `OOMKilled: false`, no memory limit set, host had 9.8Gi free throughout); not the common MongoDB-5.0+-needs-AVX crash (host CPU: AMD Ryzen 7 5700G, `avx`/`avx2` both present in `/proc/cpuinfo`).
  - the phase 0 walking-skeleton proof (2 tests, `TestConfigRepositoryIndexes`) passed cleanly on two separate startups, before crashes 1 and 3 respectively - so a freshly-started container answers a handful of queries fine; the failure is unpredictable, not tied to any single trigger identified so far.
  - docker's own `tests` service never hits this failure mode because it runs against FerretDB (Postgres-backed), not real `mongod` - this crash is unique to the new local `mongo:8` service this plan introduced.
  - **not fixed here** - root-causing a mongod segfault is outside this plan's scope and time budget. flagging for the user, with raised urgency given crash 3: worth a closer look (try `mongo:7`, check for a known `mongo:8` issue on this platform, check the host's mongodb.org compatibility matrix) before relying on this service at all, not just for full test runs.
  - container deliberately left in its crashed state (`Exited (139)`) at the end of this session as forensic evidence - `docker logs doom-bot-dev-mongo-1` to inspect, `docker compose -f docker-compose.dev.yml up -d mongo` to bring it back when ready.
  - **disposition (phase 2 triage, 2026-08-29; re-affirmed at shipdown with crash 3):** defer - needs a user decision; not blocking any phase's own dod, root-cause outside this plan's scope. no downstream phase depends on it.

  - **disposition (phase 0 triage, 2026-08-29):** defer. pre-existing, repo-wide, not caused by or fixable within this plan; not a blocker for any downstream phase here.

- **docker-path integration test gap**: `docker-compose.dev.yml`'s `tests` service has had no `.secrets` mount and no `ATTU_CONFIG_FILE` since `36f6fee` (2026-08-02, "fix(tests): test container no longer needs .env or secrets mount") stripped both in favor of `TEST_DB_URL`. that fix covered unit/component db access but never accounted for integration tests, which call `start_bot_loop()` -> `config.on_init()` and need the full toml, not just a connection string. every integration run through the sanctioned docker path (`docker compose run --build --rm tests`) has had zero chance of finding a config file since. docker-path problem, not a venv problem - needs its own fix (mount `.secrets` back in read-only for that one service, or accept integration tests don't run in that container). found 2026-08-28.
  - **disposition (phase 0 triage, 2026-08-29):** defer, standalone `item-slice` fodder - but flagged as **phase-2-relevant**: phase 2's readme rewrite documents docker as an alternative test path, and integration tests currently cannot find a config file that way. phase 2's scope revised to call this out instead of documenting docker as an unqualified working alternative.
  - **phase-2-relevance discharged (2026-08-29):** README.md's Tests section now documents docker as unit/component-only, not integration (`b3f31af`). the underlying gap (`tests` service has no `.secrets` mount) remains unfixed and still deferred.
- **`.env`'s `ATTU_CONFIG_FILE` misconfiguration**: points at `./assets/attu-bot.toml`, which doesn't exist anywhere in the repo (README documents `.secrets/attu-bot.toml` as the default). doesn't actually reach the `tests` container (no `env_file:` line on that service) so it isn't the cause of the docker-path gap above, but it's still wrong and would bite anything else that reads `.env` for this var. found 2026-08-28.
  - **disposition (phase 0 triage, 2026-08-29):** defer, standalone item-slice fodder. not a blocker for this plan's remaining phases.

## closed

- **`TEST_DB_URL` vs `database.url` precedence** - closed in `6610b61` (phase 2, 2026-08-29, resolved by reading source, no live db needed): `apps/bot/nova_core/config.py`'s `on_init()` populates `self.database` via `DatabaseConfig(**self._raw.get('database', {}))` (line 366) - a plain pydantic model (`DatabaseConfig`, line 53) with no environment-variable awareness at all. `TEST_DB_URL` does not appear anywhere in `config.py`; grepped and confirmed. it is purely a `tests/conftest.py` convention read by `_read_db_config()` for component-test fixtures that connect to mongo directly, bypassing `config.on_init()` entirely. **conclusion: they don't compete.** `database.url` (toml) is what integration tests and real bot startup use, full stop. `TEST_DB_URL` only matters for component tests. documented as two separate pointers for two separate paths in `README.md`'s Tests section (`b3f31af`).
