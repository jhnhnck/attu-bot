## closed

- **`TEST_DB_URL` vs `database.url` precedence** - closed in `6610b61` (phase 2, 2026-08-29, resolved by reading source, no live db needed): `apps/bot/nova_core/config.py`'s `on_init()` populates `self.database` via `DatabaseConfig(**self._raw.get('database', {}))` (line 366) - a plain pydantic model (`DatabaseConfig`, line 53) with no environment-variable awareness at all. `TEST_DB_URL` does not appear anywhere in `config.py`; grepped and confirmed. it is purely a `tests/conftest.py` convention read by `_read_db_config()` for component-test fixtures that connect to mongo directly, bypassing `config.on_init()` entirely. **conclusion: they don't compete.** `database.url` (toml) is what integration tests and real bot startup use, full stop. `TEST_DB_URL` only matters for component tests. documented as two separate pointers for two separate paths in `README.md`'s Tests section (`b3f31af`).

- **`mongo:8` container segfaults, both under load and idle** - closed in `dfe7a90` (2026-08-29, root-caused via `/bug-hunt`, two distinct bugs conflated as one): reproduced four times total (3 during the original plan run, 1 more on 2026-08-29 while re-checking after shipdown, before this fix).
  - **idle crash (crash 3 and the 2026-08-29 recheck, ~21-30s after a clean startup, zero test load)**: the `mongo:8` image bakes in `GLIBC_TUNABLES=glibc.pthread.rseq=0` (confirmed via `docker image inspect mongo:8`, added upstream to work around an unrelated tcmalloc perf warning). on host kernels >=6.19 (this host: `7.0.0-3-pve`) that setting trips a kernel-level rseq bug that segfaults mongod even fully idle - matches `docker-library/mongo#748` exactly (same mongod version 8.2.12, same ~30s timing, same "clean startup then total silence" log signature, same exit 139). an earlier guess (CPU shadow-stack/CET, `GLIBC_TUNABLES=glibc.cpu.hwcaps=-SHSTK`) looked plausible from a web search but was wrong and was reverted; the actual GitHub discussion thread (with primary-source, multi-hour verified testing) points at `glibc.pthread.rseq=1` specifically, now confirmed upstream as a real kernel bug (linked from the discussion: https://lore.kernel.org/all/20260428221058.149538293@kernel.org/). fix: override `GLIBC_TUNABLES=glibc.pthread.rseq=1` on the `mongo` service.
  - **load crash (crash 1 and 2, during `tests/python/component/`'s heavy collection-drop/index-teardown activity)**: docker's default 1024 fd ulimit is too low for WiredTiger under this workload; confirmed via `docker logs` showing a WiredTiger `WT_PANIC` ("Too many open files", `error_code: 24`, i.e. EMFILE) immediately before the crash. fix: `ulimits: nofile: {soft: 64000, hard: 64000}` on the `mongo` service.
  - **verification**: both fixes applied together in `docker-compose.dev.yml`; container recreated and confirmed to have both settings active inside it. idle-crash fix verified by waiting 90s past the prior crash point (Status stayed `running`). load-crash fix verified by running the full `tests/python/component/` suite (166 tests, the exact churn pattern that triggered the original EMFILE panic) - completed in 32.63s with mongo `Status: running` throughout, no crash. 11 pre-existing, unrelated `ImportError` failures remain (`fix_ccboard_recount`/`fix_ccboard_cleanup`/`fix_starboard_purge` missing from `nova_core.commands.fix`) - not a mongo issue, out of scope for this fix, not investigated further here.
