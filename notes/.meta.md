# .meta.md - AGENTS.md and notes/ System Guide

Recreatable documentation system for any repository

---

## Purpose

`AGENTS.md` is the root guidance file an AI agent reads first. `notes/` holds supplementary spec files for topics too complex for a paragraph. Together they give an agent enough context to work safely without re-exploring the codebase every session.

---

## AGENTS.md - What to Include

Structure it with these sections in order:

**1. Project Overview** - 2-3 sentences: language, runtime, deployment shape.

**2. Rules** - hard constraints for agents; short and non-negotiable (e.g. "don't commit secrets", "ask before sending messages").

**3. Architecture** - one table per major package or directory; columns: `Module | Role`.

**4. Configuration System** - where config lives, how it's loaded, precedence order.

**5. Coding Conventions** - subsections per topic:
- string quoting style
- logging: which library, which levels
- type annotation style
- linter/type-checker and strictness level
- async patterns (if applicable)
- ORM/DB patterns (if applicable)

**6. Testing** - framework, directory layout, how to run, any critical env var requirements.

**7. Running Locally** - step-by-step; be explicit about prerequisites.

**8. Patterns & Pitfalls** - the most valuable section; a numbered list of non-obvious gotchas discovered during development. write these reactively as bugs surface.

**9. Reference Notes** - links to `notes/` files with one-line descriptions.

**10. File & Directory Layout** - a `tree`-style listing of the project root.

**11. Personality / Style** - if comments or docs have a voice, document it here.

## notes/ - When to Create a File

Create a note file when a topic is:
- **complex enough** that it needs more than a paragraph in `AGENTS.md`
- **stable enough** that it won't change every week
- **referenceable** - something an agent would look up mid-task

Common note types:

| File | Contents |
|---|---|
| `<feature>.md` | behavior rules (numbered), storage schema, key functions table, commands table |
| `testing.md` | test directory layout, fixture naming, mocking strategy, how to run |
| `<library>_usage.md` | wrapper functions, raw API fallback, limits and gotchas, working examples |
| `comment_style.md` | good/bad examples, tag conventions, what not to do |
| `<domain_concept>.md` | math/logic spec, pseudocode, code file references |

Add a note file the second time you find yourself re-explaining the same thing to an agent - that's the signal to write it down.

---

## Writing Style

- tables for reference info (configs, commands, functions, API limits)
- numbered lists for sequences (resolution order, calculation steps, migration history)
- code blocks with inline comments for examples
- directive tone: "do X", "don't Y" - not suggestions
- link between files: `AGENTS.md` links to notes; notes can cross-reference each other
- include migration history in schema docs so agents know what changed and why

## Minimal Starting Template

```
AGENTS.md               <- always read first
notes/
  style/                <- conventions and usage patterns
    comment_style.md    <- if you have non-obvious style rules
    message_style.md    <- tone, capitalization, error format
    <library>_usage.md  <- one file per library with non-obvious patterns
  features/             <- feature specs and system docs
    <feature>.md        <- one file per complex subsystem
  dev/                  <- development guides
    testing.md          <- test layout and how to run
    dev_setup.md        <- local setup, deploy steps
  .meta.md              <- this file
```
